Production MLOps & GitOps Architecture

An enterprise-grade system design reference manual detailing the architecture, design choices, infrastructure tiers, and operations of the ml-serving-capstone platform.

01 End-to-End System Topology

The system is architected as a complete decoupled cloud-native MLOps platform. Workloads are reconciled declaratively via GitOps, with zero inbound firewall ports required for continuous deployment.

The cluster is partitioned cleanly: infrastructure services like ArgoCD live in the argocd administrative namespace, while application workloads, caches, and streaming brokers are isolated in the ml-serving workload namespace.

02 Core Application Tier: Dual-Path ML Serving

Why Dual-Path Serving?

Real-world production ML serving requires handling two vastly different traffic profiles:

Serving Path Mechanism Primary Use Case Latency Profile
1. Synchronous Online Path REST API (FastAPI / HTTP) User-facing interactive applications, real-time UI queries Low Latency (< 15ms target)
2. Asynchronous Streaming Path Apache Kafka (Event-Driven) High-volume batch pipelines, IoT ingest, telemetry processing High Throughput (Decoupled, zero backpressure)

A. The Model Layer (model.py)

In this capstone, the inference engine wraps a Scikit-Learn LinearRegression model representing a linear function ($y = 2x$):

def get_model() -> LinearRegression:
    """Returns a singleton trained scikit-learn model."""
    X = np.array([[1], [2], [3], [4]])
    y = np.array([2, 4, 6, 8])
    model = LinearRegression()
    model.fit(X, y)
    return model
Production Scalability Tip: While this model fits in memory instantly, in deep learning systems (e.g. PyTorch LLMs, Vision transformers), model weights take seconds or minutes to load from disk. That is why Readiness Probes are critical—they prevent Kubernetes from sending queries to an uninitialized model!

B. The HTTP API Layer (main.py)

Built with FastAPI and Pydantic v2 for automatic schema validation and serialization:

  • POST /predict: Accepts a list of floats (input_data: list[float]) and returns predictions.
  • GET /healthz: Liveness probe verifying the Python event loop is unblocked.
  • GET /readyz: Readiness probe verifying that the ML model is initialized in RAM.

C. The Asynchronous Worker Layer (kafka_worker.py)

Uses aiokafka to create an asynchronous loop that reads from the inference-requests topic, executes batch prediction, and pushes results to inference-results with tracking IDs.

03 Caching Strategy & Graceful Degradation

Predictive Caching Mechanics

ML inference is CPU/GPU intensive. If multiple clients query the same input features, recalculating the dot-products is wasted compute. We implemented an MD5 cryptographic cache key design in redis_cache.py:

def cache_key(input_data: list[float]) -> str:
    # 1. Deterministically serialize the floating point input array
    input_str = json.dumps(input_data, sort_keys=True)
    # 2. Hash into fixed-length 32-character hexadecimal digest
    hash_input = hashlib.md5(input_str.encode()).hexdigest()
    # 3. Namespace with model version to prevent stale cache on model retraining
    return f"pred:{MODEL_VERSION}:{hash_input}"

Why Version the Cache Key?

If you retrain your model from v1 to v2, old predictions cached in Redis would return invalid results for identical inputs! By namespacing the key with MODEL_VERSION, updating the version string automatically invalidates all previous cached values without manual cache flushing!

The Graceful Degradation Design Pattern

In distributed systems, external dependencies will fail. Network partitions happen, and Redis pods restart. A junior mistake is allowing Redis connection timeouts to bubble up as HTTP 500 errors to end users.

Our implementation treats the cache as an optimization, not a hard requirement:

async def get_cached_prediction(input_data: list[float]) -> list[float] | None:
    try:
        key = cache_key(input_data)
        cached_value = await redis_client.get(key)
        if cached_value is not None:
            return json.loads(cached_value)
    except Exception as e:
        # LOG AND FALLBACK: The API remains completely functional!
        logger.warning(f"Redis cache lookup failed: {e}. Falling back to model inference.")
    return None

04 Kubernetes Runtime & Hardening

A. Resource Quotas (Requests vs. Limits)

Every pod template in our chart defines strict compute boundaries:

resources:
  requests:
    cpu: 100m      # 0.1 CPU core reserved exclusively for this pod
    memory: 128Mi  # 128 Megabytes guaranteed RAM
  limits:
    cpu: 500m      # Hard throttle ceiling if pod spikes
    memory: 512Mi  # Kernel sends SIGKILL (OOMKilled) if exceeded
  • Requests are used by the Kubernetes Scheduler to decide which physical node has enough capacity to host the pod.
  • Limits are enforced by Linux kernel cgroups to prevent any single container from starving adjacent pods of CPU or memory (Noisy Neighbor problem).

B. Pod Security Standards (CIS Benchmark Compliance)

In our Dockerfile and Helm templates, we enforce unprivileged execution:

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 1000
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL

If an attacker discovers a remote code execution exploit in an open-source Python library, they are trapped in a sandbox with zero root privileges and no Linux kernel capabilities.

C. Apache Kafka in KRaft Mode (No ZooKeeper)

Historically, Kafka required an entire auxiliary Apache ZooKeeper cluster to maintain metadata, leading to split-brain bugs, complex maintenance, and high memory footprints. Our setup deploys KRaft (Kafka Raft Metadata Mode):

  • Kafka brokers use an internal Raft consensus algorithm directly.
  • Startup time dropped from minutes to under 5 seconds.
  • Zero external ZooKeeper dependency!

05 Helm Packaging & Templating Mastery

Helm acts as both a package manager and a parameterization engine. It allows maintaining a single set of declarative YAML templates while deploying to Development, Staging, and Production with different parameters.

Chart Anatomy

helm/ml-serving-capstone/
├── Chart.yaml                  # Metadata, semantic version (SemVer), API version

    ├── _helpers.tpl            # Reusable Go template functions & labels

Standard Kubernetes Labels (_helpers.tpl)

Notice how our Helm templates use the standard Kubernetes labels defined in _helpers.tpl:

These labels allow service meshes (Istio/Linkerd), metrics collectors (Prometheus), and log aggregators (Splunk/Fluent Bit) to query and index pods effortlessly.

06 GitOps with ArgoCD Engine

How ArgoCD Reconciles Desired vs. Live State

ArgoCD operates on a continuous feedback loop:

  1. Target State (Git): Reads the Helm templates and values.yaml in GitHub.
  2. Live State (Cluster): Queries the Kubernetes API server for active Deployments and Services.
  3. Reconciliation Loop: Calculates a diff between Git and Cluster. If a difference exists, the status changes to OutOfSync.

What is Self-Healing (selfHeal: true)?

Try this in your terminal right now: run microk8s kubectl delete deployment ml-serving-capstone -n ml-serving.
Within 3 seconds, ArgoCD detects that the live cluster violates the contract committed to Git, and automatically recreates the entire deployment! Manual human errors or unauthorized modifications are immediately corrected.

The Declarative ArgoCD CRD (argocd/application.yaml)

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: ml-serving-capstone
  namespace: argocd
  finalizers:
    # Cascading deletion: deleting the ArgoCD app also cleans up all child resources
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: 'https://github.com/mastershantash/project-one.git'
    targetRevision: main
    path: ml-serving-capstone/helm/ml-serving-capstone
    helm:
      valueFiles:
        - values.yaml
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: ml-serving
  syncPolicy:
    automated:
      prune: true     # Deletes objects from K8s when removed from Git
      selfHeal: true  # Reverts manual kubectl tampering
    syncOptions:
      - CreateNamespace=true

08 Production Observability & Splunk Integration

The Log Transport Pipeline

In distributed cloud environments, logging into a local file (e.g. app.log) is an anti-pattern because containers are ephemeral. If a pod crashes, its local disk is wiped!

Instead, the 12-Factor App methodology (Factor XI: Logs) mandates writing all events as structured JSON directly to stdout and stderr.

+----------------------+ +----------------------+ | FastAPI App Pod | | Kafka Worker Pod | | (Writes to stdout) | | (Writes to stdout) | +----------------------+ +----------------------+ | | +--------------+--------------+ v +----------------------------------+ | Kubelet writes to Host Node Path | | /var/log/pods/*/*.log | +----------------------------------+ | v +----------------------------------+ | Fluent Bit (DaemonSet Agent) | | - Enriches logs with K8s Pod Name| | - Appends Namespace & Labels | +----------------------------------+ | | HTTP POST (JSON Events) v +----------------------------------+ | Splunk HTTP Event Collector (HEC)| | Port: 8088 / Index: ml_workloads | +----------------------------------+

Essential Splunk Queries for MLOps

# 1. Track API Latency Percentiles (p50, p95, p99)
index=ml_workloads sourcetype=fastapi
| stats avg(duration_ms) as avg_lat, p95(duration_ms) as p95_lat, p99(duration_ms) as p99_lat by endpoint

# 2. Monitor Redis Cache Hit vs. Miss Ratio
index=ml_workloads "cache"
| stats count by status
| eval hit_rate = (hit / (hit + miss)) * 100

# 3. Detect Out-of-Memory (OOM) or Pod Restarts
index=kube_events reason="OOMKilled" OR reason="BackOff"
| table _time, pod_name, namespace, reason, message

10 Senior MLOps & DevOps Revision Q&A

Use these scenario-based interview questions to test your conceptual mastery of this stack:

Q1: Why is GitOps (Pull model) considered strictly superior to traditional CI/CD (Push model) for Kubernetes security?

Answer: In the traditional push model, your CI server (e.g. Jenkins or GitHub Actions runner) must possess permanent administrative KUBECONFIG credentials to the production cluster. If your CI system or any third-party build action is compromised, attackers gain full root control of your Kubernetes cluster. In the GitOps pull model, the cluster never accepts inbound connections; ArgoCD runs inside the cluster behind firewalls and pulls manifests unidirectionally from Git.

Q2: What is the exact difference between a Liveness Probe and a Readiness Probe?

Answer: A Liveness Probe detects whether the process is deadlocked or frozen; if it fails, Kubernetes terminates and restarts the container. A Readiness Probe detects whether the container is ready to accept user requests (e.g. heavy model weights loaded into memory); if it fails, Kubernetes does NOT kill the pod, but temporarily removes it from the Service endpoints so users never receive 502/503 errors.

Q3: Why did we use Apache Kafka in KRaft mode instead of with ZooKeeper?

Answer: KRaft (Kafka Raft Metadata mode) integrates consensus directly into Kafka brokers. It eliminates the separate ZooKeeper JVM processes, drastically reduces RAM usage, prevents metadata synchronization discrepancies, and accelerates cluster recovery from minutes to seconds.

Q4: How does our Dockerfile utilize layer caching with `uv`?

Answer: We first copy only pyproject.toml, uv.lock, and README.md, running uv sync --frozen --no-dev --no-install-project. This downloads and caches all external third-party Python wheels in an isolated Docker layer. We only copy src/ in a later step. When developers change application code, Docker skips downloading wheels and rebuilds in less than 2 seconds.

Q5: Why did we implement non-root user execution (`UID 1000`)?

Answer: Running containers as root is a violation of Kubernetes PodSecurityStandards. If an application dependency has an escape vulnerability, a root container process can compromise the underlying Linux host kernel. Running as unprivileged user 1000 prevents privilege escalation.
