Architectural Insight: The GIL & ML Serving

In Java, parallelizing 1,000 requests across 16 CPU cores is done by spinning up worker threads. In Python, the Global Interpreter Lock (GIL) restricts bytecode execution to one thread per process. However, C-extensions like scikit-learn, numpy, and torch release the GIL during matrix math and numerical calculations! For HTTP routing and caching, asynchronous I/O (FastAPI + Redis) handles 10,000+ concurrent network connections on a single thread. Multiple CPU cores are leveraged by launching multiple Uvicorn workers or scaling Kubernetes Pod replicas.

Why uv over Pip & Conda?

In Java, Maven resolves artifacts and caches them locally in ~/.m2/repository. Traditional Python tools (pip, virtualenv) re-download and re-compile wheels per project. uv uses a global content-addressable cache and hardlinks files into virtual environments in milliseconds — making it 10x to 100x faster than pip and poetry.

04. The ML Model Serving Logic (model.py)

The model module encapsulates the machine learning model lifecycle: training/loading weights, caching the instance in memory as a singleton, and executing vector-based inference using NumPy and scikit-learn.

+-----------------------------------------------------------------------------------+ | CPU-BOUND ML INFERENCE & THE GIL EXECUTION MODEL | +-----------------------------------------------------------------------------------+ | | | [HTTP Inbound Request] | | | | | v | | +-------------------------------+ | | | Uvicorn Event Loop (AsyncIO) | Single thread handles 10,000+ concurrent I/O | | +-------------------------------+ | | | | | v (Awaits non-blocking Redis lookup) | | +-------------------------------+ | | | Cache Miss: Call get_model() | Returns memoized LinearRegression singleton | | +-------------------------------+ | | | | | v | | +-------------------------------+ | | | model.predict(X_new) | Releases GIL! Matrix math executes in | | +-------------------------------+ optimized C / Fortran OpenBLAS SIMD vector | | instructions at bare-metal speeds. | +-----------------------------------------------------------------------------------+
src/ml_serving_capstone/model.py 
from functools import lru_cache

import numpy as np
from sklearn.linear_model import LinearRegression


def predict(model: LinearRegression, X_new: np.ndarray) -> np.ndarray:
    """
    Make predictions using the trained linear regression model.

    Parameters:
    model (LinearRegression): Trained linear regression model.
    X_new (array-like): New input data for prediction.

    Returns:
    np.ndarray: Predicted values for the input data.
    """
    return model.predict(X_new)  # Make predictions


def evaluate_model(
    model: LinearRegression, X_test: np.ndarray, y_test: np.ndarray
) -> float:
    """
    Evaluate the trained linear regression model on test data.

    Parameters:
    model (LinearRegression): Trained linear regression model.
    X_test (array-like): Feature matrix for testing.
    y_test (array-like): Target vector for testing.

    Returns:
    float: R^2 score of the model on the test data.
    """
    return float(model.score(X_test, y_test))


@lru_cache
def get_model() -> LinearRegression:
    """
    Singleton factory for the trained ML model.
    The @lru_cache decorator ensures the model weights are instantiated
    and trained exactly once in memory across the entire worker process.
    """
    X = np.array([[1], [2], [3], [4]])
    y = np.array([2, 4, 6, 8])
    model = LinearRegression()
    model.fit(X, y)  # training happens here, guaranteed, before anyone gets the model
    return model
Java Comparison: @lru_cache as Spring @Bean Singleton

In Spring Boot, you declare a @Bean with default singleton scope so heavy objects are only initialized once on startup. Python's @lru_cache(maxsize=1) decorates a function to memoize its return value, preventing expensive model re-instantiation on every incoming HTTP request.

05. Asynchronous Redis Caching Layer (redis_cache.py)

High-throughput ML endpoints must protect downstream compute from redundant inference. We implement an asynchronous cache backed by Redis with versioned keys, MD5 input hashing, and a fail-open defensive resilience pattern.

+-----------------------------------------------------------------------------------+ | FAIL-OPEN PREDICTIVE CACHING ARCHITECTURE | +-----------------------------------------------------------------------------------+ | | | Incoming Features: [5.0, 10.0] | | | | | v | | MD5 Canonical Hash: "a8f5c31e..." | | Scoped Cache Key: "pred:v1:a8f5c31e..." | | | | | +--------------------------------------+ | | | | | | v (Try Async Redis Get) v (Redis Down / Network Timeout) | | [Redis Connection Pool] [Shielded Exception Catch] | | / \ | | | HIT MISS | Log warning | | | \ v | | Return Cached JSON +---------------------> [Direct Model Inference] | | (p95: 1.2ms) [100% Zero-Drop SLA] | +-----------------------------------------------------------------------------------+
src/ml_serving_capstone/redis_cache.py 
import hashlib
import json
import logging
import os

import redis.asyncio as redis

logger = logging.getLogger(__name__)

# Key design: include model version to prevent cache pollution during zero-downtime model rollouts
MODEL_VERSION = "v1"
REDIS_HOST = os.getenv("REDIS_HOST", "localhost")
REDIS_PORT = int(os.getenv("REDIS_PORT", "6379"))

# Non-blocking async connection pool with aggressive timeouts to prevent socket exhaustion
redis_client = redis.Redis(
    host=REDIS_HOST,
    port=REDIS_PORT,
    decode_responses=True,
    socket_timeout=1.0,
    socket_connect_timeout=1.0,
)


def cache_key(input_data: list[float]) -> str:
    """Generate a deterministic, version-scoped MD5 cache key."""
    input_str = json.dumps(input_data, sort_keys=True)
    hash_input = hashlib.md5(input_str.encode()).hexdigest()
    return f"pred:{MODEL_VERSION}:{hash_input}"


async def cache_prediction(input_data: list[float], predictions: list[float]) -> None:
    """
    Cache predictions with a 1-hour TTL.
    Fail-open design: if Redis is unreachable, catch exception, log warning, and do not fail the request.
    """
    try:
        key = cache_key(input_data)
        await redis_client.set(key, json.dumps(predictions), ex=3600)
    except Exception as e:
        logger.warning(f"Redis cache write failed: {e}. Proceeding without caching.")


async def get_cached_prediction(input_data: list[float]) -> list[float] | None:
    """
    Look up predictions in Redis.
    Fail-open design: return None on network failure, falling back seamlessly to model inference.
    """
    try:
        key = cache_key(input_data)
        cached_value = await redis_client.get(key)
        if cached_value is not None:
            return json.loads(cached_value)
    except Exception as e:
        logger.warning(f"Redis cache lookup failed: {e}. Falling back to model inference.")
    return None

06. FastAPI Serving REST API (main.py)

The REST service is built with FastAPI. It defines strict request/response DTO schemas with Pydantic v2, provides Kubernetes liveness (/healthz) and readiness (/readyz) probes, and emits structured JSON logs with millisecond latency metrics.

src/ml_serving_capstone/main.py 
import json
import logging
import time

import numpy as np
from fastapi import FastAPI
from prometheus_fastapi_instrumentator import Instrumentator
from pydantic import BaseModel

from .model import get_model, predict
from .redis_cache import MODEL_VERSION, cache_prediction, get_cached_prediction

logger = logging.getLogger("ml_serving")
logging.basicConfig(level=logging.INFO, format="%(message)s")


class PredictRequest(BaseModel):
    """
    Request model for prediction endpoint.
    Strictly validated by Pydantic: ensures input_data is a list of floats.
    """
    input_data: list[float]


class PredictResponse(BaseModel):
    """
    Response model for prediction endpoint.
    """
    predictions: list[float]


app = FastAPI(title="ML Serving Capstone API", version="0.1.0")

# Expose /metrics endpoint for Prometheus scraping
Instrumentator().instrument(app).expose(app)


@app.get("/healthz")
async def healthz():
    """
    Kubernetes Liveness Probe: Checks if the web process is running.
    If this fails, K8s restarts the container.
    """
    return {"status": "healthy"}


@app.get("/readyz")
async def readyz():
    """
    Kubernetes Readiness Probe: Verifies model weights are loaded and ready.
    If this fails, K8s stops routing ingress traffic to this Pod.
    """
    try:
        model = get_model()
        if model is None:
            return {"status": "not_ready", "reason": "model not loaded"}, 503
        return {"status": "ready"}
    except Exception as e:
        return {"status": "not_ready", "error": str(e)}, 503


@app.post("/predict", response_model=PredictResponse)
async def predict_endpoint(request: PredictRequest):
    """
    Prediction endpoint with cache check, model inference, and structured logging.
    """
    start_time = time.perf_counter()
    
    # 1. Check Redis Cache
    cached_predictions = await get_cached_prediction(request.input_data)
    if cached_predictions is not None:
        latency_ms = round((time.perf_counter() - start_time) * 1000, 2)
        logger.info(
            json.dumps(
                {
                    "event": "model_inference",
                    "model_version": MODEL_VERSION,
                    "cache_hit": True,
                    "latency_ms": latency_ms,
                    "input_features": request.input_data,
                    "predictions": cached_predictions,
                }
            )
        )
        return PredictResponse(predictions=cached_predictions)

    # 2. Cache Miss: Execute Model Inference
    model = get_model()
    X_new = np.array(request.input_data).reshape(-1, 1)
    predictions = predict(model, X_new)
    
    # 3. Asynchronously write result to cache
    await cache_prediction(request.input_data, predictions.tolist())

    latency_ms = round((time.perf_counter() - start_time) * 1000, 2)
    logger.info(
        json.dumps(
            {
                "event": "model_inference",
                "model_version": MODEL_VERSION,
                "cache_hit": False,
                "latency_ms": latency_ms,
                "input_features": request.input_data,
                "predictions": predictions.tolist(),
            }
        )
    )
    return PredictResponse(predictions=predictions.tolist())

08. Event-Driven Kafka Streaming Worker (kafka_worker.py)

In addition to synchronous REST serving, enterprise architectures frequently demand asynchronous stream processing. The worker consumes events from an input topic, runs model inference, and publishes results to an egress topic using aiokafka with automated reconnection retries.

src/ml_serving_capstone/kafka_worker.py 
import asyncio
import json
import logging
import os

import numpy as np
from aiokafka import AIOKafkaConsumer, AIOKafkaProducer

from .model import get_model, predict

logger = logging.getLogger(__name__)

KAFKA_BOOTSTRAP_SERVERS = os.getenv("KAFKA_BOOTSTRAP_SERVERS", "localhost:9092")
INFERENCE_REQUESTS_TOPIC = os.getenv("INFERENCE_REQUESTS_TOPIC", "inference-requests")
INFERENCE_RESULTS_TOPIC = os.getenv("INFERENCE_RESULTS_TOPIC", "inference-results")
KAFKA_GROUP_ID = os.getenv("KAFKA_GROUP_ID", "ml-serving-capstone")


async def run_worker() -> None:
    logger.info(f"Connecting Kafka worker to {KAFKA_BOOTSTRAP_SERVERS}...")
    consumer = None
    producer = None

    # Resilient retry loop with backoff for cluster cold-starts
    while True:
        try:
            consumer = AIOKafkaConsumer(
                INFERENCE_REQUESTS_TOPIC,
                bootstrap_servers=KAFKA_BOOTSTRAP_SERVERS,
                group_id=KAFKA_GROUP_ID,
            )
            producer = AIOKafkaProducer(bootstrap_servers=KAFKA_BOOTSTRAP_SERVERS)
            await consumer.start()
            await producer.start()
            logger.info(f"Connected to Kafka! Listening on '{INFERENCE_REQUESTS_TOPIC}'...")
            break
        except Exception as e:
            logger.warning(f"Kafka not ready ({e}). Retrying in 5 seconds...")
            if consumer:
                await consumer.stop()
            if producer:
                await producer.stop()
            await asyncio.sleep(5)

    try:
        async for msg in consumer:
            try:
                request = json.loads(msg.value)
                model = get_model()
                X_new = np.array(request["input_data"]).reshape(-1, 1)
                prediction = predict(model, X_new).tolist()
                result = json.dumps({"id": request.get("id"), "predictions": prediction})
                await producer.send_and_wait(INFERENCE_RESULTS_TOPIC, result.encode())
            except Exception as e:
                logger.error(f"Error processing message: {e}")
    finally:
        logger.info("Stopping Kafka consumer and producer...")
        if consumer:
            await consumer.stop()
        if producer:
            await producer.stop()


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO, format="%(asctime)s [%(levelname)s] %(message)s")
    asyncio.run(run_worker())

2. Deep Dive: CoreDNS Resolution & The ndots:5 Trap

Kubernetes injects ndots:5 in every pod's /etc/resolv.conf by default. If your application attempts to connect to redis-service without a namespace suffix, CoreDNS sequentially queries:

  1. redis-service.ml-app.svc.cluster.local (Fails with NXDOMAIN because Redis is in ml-infra!)
  2. redis-service.svc.cluster.local (Fails)
  3. redis-service.cluster.local (Fails)
  4. redis-service.<node-search-domain> (Fails)

This generates 4 wasted DNS lookup roundtrips per connection attempt, adding 15–50ms of artificial latency! By strictly supplying the Fully Qualified Domain Name (FQDN) redis-service.ml-infra.svc.cluster.local, CoreDNS resolves the IP on the first attempt with zero wasted hops.

20. ArgoCD GitOps Engine Installation (Deep Dive: Server-Side Apply)

ArgoCD operates as the in-cluster GitOps controller, continuously reconciling the live cluster state with the desired state committed to Git.

Deep Dive: Client-Side vs Server-Side Apply (The 262,144 Byte Limit)

In standard kubectl apply (client-side), kubectl serializes the entire previous manifest into the kubectl.kubernetes.io/last-applied-configuration annotation in ETCD. ETCD enforces a hard ceiling of 256 KB (262,144 bytes) on annotations. ArgoCD's CustomResourceDefinitions contain enormous OpenAPI v3 validation schemas (exceeding 300KB), immediately crashing client-side apply! Server-Side Apply (SSA) sends the raw YAML to the Kubernetes API server, which tracks field ownership directly in ETCD metadata using a compact field-management protocol, completely bypassing annotation limits.

# 2. Install stable manifests using server-side apply

# 3. Patch ArgoCD API Server to NodePort 30781
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "NodePort", "ports": [{"port": 443, "nodePort": 30781, "targetPort": 8080}]}}'

# 4. Retrieve initial admin password (decoded from Secret)
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d && echo

# URL: https://localhost:30781 (User: admin / Password: <retrieved-password>)

26. Production War Stories: 12 Battle-Tested Bugs & Fixes

Real-world production engineering is defined by diagnosing and resolving edge-case failures. Below are the 12 critical errors resolved during the construction of this platform.

War Story 1: ArgoCD CRD Metadata Exceeded 262KB Limit

Symptom: kubectl apply -f install.yaml failed with CustomResourceDefinition.apiextensions.k8s.io "applications.argoproj.io" is invalid: metadata.annotations: Too long: must have at most 262144 bytes.

Root Cause: Client-side apply calculates a JSON diff and stores the entire previous manifest in the kubectl.kubernetes.io/last-applied-configuration annotation. Large OpenAPI v3 schemas exceed this ETCD limit.

Fix: Install using Kubernetes server-side apply: kubectl apply -n argocd -f ... --server-side.

War Story 2: Helm Go Template Collision in Grafana & Prometheus Alerts

Symptom: helm lint helm/ml-infra failed with parse error at (grafana.yaml:62): function "status" not defined and undefined variable "$labels".

Root Cause: Grafana and Prometheus use {{status}} and {{ $labels.instance }}. Helm's Go template engine intercepted these as Helm variables.

Fix: Escape template variables using Go raw string literals: {{ `{{status}}` }} and {{ `{{ $labels.instance }}` }}.

War Story 3: Fluent Bit Localhost Inaccessibility to Splunk

Symptom: Fluent Bit logs reported [error] [output:http:http.0] connection failed to 127.0.0.1:8088.

Root Cause: Inside a Kubernetes container, 127.0.0.1 routes to the Pod's loopback network interface, not the physical host where Splunk was running.

Fix: Bound Fluent Bit to the host's actual LAN interface IP (192.168.29.122:8088) with tls.verify Off for self-signed certificates.

War Story 4: Kafka KRaft Controller Cold-Start Quorum Race

Symptom: The topic creation Job crashed in a CrashLoopBackOff with LEADER_NOT_AVAILABLE or connection refused.

Root Cause: In KRaft mode, metadata quorum consensus takes 5–10 seconds on first launch. The Job attempted topic creation before the broker opened port 9092.

Fix: Implemented a Kubernetes initContainer that polls kafka-broker-api-versions.sh --bootstrap-server kafka-service:9092 until healthy.

War Story 5: Ruff Linter BLE001 & Import Sorting CI Breakage

Symptom: GitHub Actions CI failed with BLE001: Do not catch blind exception: Exception in redis_cache.py and I001: Import block is un-sorted.

Root Cause: Ruff default rules flag broad exception catching as an anti-pattern. However, in our fail-open cache design, catching broad exceptions is intentional to protect API availability.

Fix: Added [tool.ruff.lint] ignore = ["BLE001"] in pyproject.toml and ran uv run ruff check --fix ..

War Story 6: ArgoCD Multi-Application ClusterRoleBinding Conflict

Symptom: ArgoCD reported SharedResourceWarning: ClusterRoleBinding/fluent-bit-read is part of applications ml-infra and ml-serving-capstone.

Root Cause: Migrating from a monolithic Helm chart to decoupled charts resulted in both applications attempting to manage the same cluster-scoped RBAC resource.

Fix: Deleted the legacy monolithic application from ArgoCD, allowing ml-infra to establish sole ownership.

War Story 7: Rolling Deployment Port-Forward Socket Severance

Symptom: Subsequent curl requests to http://localhost:8001 exited with code 52 (Empty reply from server).

Root Cause: kubectl port-forward maintains an active TCP tunnel directly to the backing Pod IP. When ArgoCD rolled out a new deployment, the old Pod terminated, dropping the socket.

Fix: Restarted port-forward daemon pointing to svc/ml-app so connections route to healthy replacement replicas.

War Story 8: Cached :latest Tag Masking Production Code

Symptom: The Pod was running, but newly added /metrics endpoint returned 404.

Root Cause: Kubernetes pods used imagePullPolicy: IfNotPresent with the :latest tag. The node cached the initial image and never pulled subsequent builds.

Fix: Switched to immutable Git SHA tagging (sha-${SHORT_SHA}) and set imagePullPolicy: Always in Helm values.

War Story 9: Cross-Namespace DNS Search Domain Latency

Symptom: Workloads in ml-app failed to connect to Redis when configured as redis-service.

Root Cause: Kubernetes default CoreDNS search paths only append the local namespace (ml-app.svc.cluster.local). Unqualified names fail to resolve across namespaces.

Fix: Configured cross-namespace DNS targets explicitly: redis-service.ml-infra.svc.cluster.local.

War Story 10: Async Redis Connection Pool Socket Exhaustion

Symptom: Under high concurrent load, requests hung and threw ConnectionTimeoutError.

Root Cause: Unbounded socket creation without explicit connection pool timeouts exhausted available file descriptors on the node.

Fix: Configured socket_timeout=1.0 and socket_connect_timeout=1.0 directly on the redis.Redis client singleton.

War Story 11: Non-Root User Permission Denied in Docker

Symptom: Container crashed on startup with PermissionError: [Errno 13] Permission denied: '/app/.venv'.

Root Cause: Dependencies were installed as root, but runtime process was switched to USER appuser (UID 1000).

Fix: Ran chown -R appuser:appgroup /app and executed uv sync directly as USER appuser.

War Story 12: Monorepo Infinite GitOps CI Loop

Symptom: CI built an image, pushed an updated values.yaml commit to the repository, which triggered a new CI run infinitely.

Root Cause: Co-locating application source and deployment manifests within the same Git repository created a recursive trigger loop.

Fix: Decoupled into a Polyrepo architecture: project-one (App) triggers cross-repo writebacks to project-one-gitops (Platform), while ArgoCD watches only the GitOps repository.

27. Senior Engineering Revision Q&A: Architectural Deep-Dive

15 technical questions designed to test deep mastery of Python MLOps, distributed systems, Kubernetes, and GitOps.

Q1: How does the Python GIL affect high-throughput ML serving compared to the JVM?

The Global Interpreter Lock prevents multiple native threads from executing Python bytecodes simultaneously. In Java, thread pools handle concurrent HTTP requests and computations across CPU cores. In Python, I/O operations (FastAPI, Redis, Kafka) release the GIL during async wait states. Furthermore, numerical libraries like NumPy and scikit-learn execute in optimized C/Fortran routines that release the GIL during matrix computations. To scale across multiple CPU cores, we scale out Kubernetes Pod replicas or launch multiple Uvicorn worker processes.

Q2: Why use Pydantic v2 over standard Python dataclasses or Marshmallow?

Pydantic v2 is built on pydantic-core, written in Rust. It performs serialization, parsing, and type validation at native machine-code speeds (5x to 50x faster than pure-Python libraries). It also seamlessly generates OpenAPI JSON schemas used by FastAPI to construct interactive Swagger documentation automatically.

Q3: What is the exact difference between Kubernetes Liveness and Readiness probes?

A Liveness Probe (/healthz) tests whether the container runtime is healthy. If it fails, kubelet terminates and restarts the Pod container. A Readiness Probe (/readyz) tests whether the application is prepared to serve user traffic (e.g., model weights are initialized and warm). If it fails, Kubernetes leaves the Pod running but removes its IP from the Endpoints object of the Service, ensuring zero dropped requests during cold starts.

Q4: Why is GitOps pull-based reconciliation fundamentally superior to push-based CI deployment?

Push-based CI (e.g., running helm upgrade or kubectl apply inside GitHub Actions) requires storing high-privilege cluster admin credentials inside external CI runners, creating an expanded security attack surface. Furthermore, push-based pipelines cannot detect or revert configuration drift caused by manual in-cluster changes. ArgoCD operates entirely inside the cluster (zero inbound firewall openings), continuously diffs the cluster against Git, and automatically self-heals drifts.

Q5: Why did we implement an MD5 hash prefix in the Redis cache key?

Machine learning inference features can be arbitrarily large floating-point arrays. Using raw string arrays as Redis keys leads to excessive memory consumption in Redis and unpredictable key lengths. Hashing the canonical JSON representation into an MD5 digest yields a fixed-length 32-character string. Scoping the key with pred:{MODEL_VERSION}:{hash} guarantees zero cache contamination when new model weights are deployed.

Q6: Why is the fail-open caching pattern essential for mission-critical ML microservices?

Redis is an optimization layer, not a source of truth. If Redis suffers a network partition, cluster restart, or socket exhaustion, a fail-closed implementation would crash user requests with HTTP 500. A fail-open pattern catches the network exception, emits a warning log, and falls back to model inference, ensuring 100% API availability at the minor cost of temporary latency increases.

Q7: How does KRaft mode in Apache Kafka eliminate ZooKeeper dependencies?

KRaft (Kafka Raft Metadata Mode) uses an internal Raft consensus protocol to manage metadata directly within Kafka brokers. Metadata is stored in a replicated event topic (@metadata), eliminating external synchronization lag, reducing memory overhead, and enabling near-instantaneous controller failover.

Q8: Why does the topic provisioning Job require an initContainer?

Kubernetes starts all Pods declared in a Helm chart in parallel unless dependency barriers are enforced. If the topic creation Job executes immediately, Kafka might still be electing a KRaft controller quorum, causing the Job to crash. The init container uses kafka-broker-api-versions.sh to poll port 9092, ensuring the topic creation container runs only when the broker is accepting requests.

Q9: Why does ArgoCD require --server-side apply during installation?

Client-side kubectl apply serializes the complete applied configuration into the kubectl.kubernetes.io/last-applied-configuration annotation. ETCD enforces a hard limit of 262,144 bytes on annotations. ArgoCD's OpenAPI v3 validation schemas in its CRDs exceed this limit. Server-side apply stores the schema directly in the API server's field management registry without using annotations.

Q10: Why must container images in Kubernetes be tagged with immutable Git SHAs rather than :latest?

The :latest tag is a mutable pointer. When Kubernetes nodes cache :latest, subsequent deployments using imagePullPolicy: IfNotPresent will not pull new image builds, causing pods to run outdated code. Furthermore, using :latest breaks GitOps rollback semantics, since Git cannot determine which binary corresponds to which commit. Immutable tags like sha-c0a5d5d ensure 100% reproducibility and auditability.

Q11: Why is multi-stage Docker build essential for security and speed?

In single-stage Docker builds, compilers (gcc, g++), package managers (uv, pip), and build headers remain in the final image, bloating container size and introducing vulnerabilities (CVEs). Multi-stage builds compile artifacts in an ephemeral builder container and copy only the runtime virtual environment into a minimal base image.

Q12: How does Prometheus scrape metrics from ephemeral Pods in Kubernetes?

Prometheus uses Kubernetes Service Discovery (kubernetes_sd_configs: [{role: pod}]). It queries the Kubernetes API server for Pods annotated with prometheus.io/scrape: "true", extracts their IP and port from annotations, and dynamically builds scrape targets.

Q13: How does Fluent Bit reliably ship Kubernetes container logs to Splunk?

Fluent Bit runs as a DaemonSet on every Kubernetes node, mounting the host's /var/log/pods directory. The tail input plugin streams container log files, the kubernetes filter queries the API server to enrich logs with Pod names and namespaces, and the http output plugin POSTs structured JSON events to Splunk's HTTP Event Collector (HEC) on port 8088.

Q14: What prevents infinite build loops in our Polyrepo CI/CD architecture?

The App repo CI triggers only on changes to ml-serving-capstone/. When it builds a new container image, it performs a writeback to the GitOps repo (project-one-gitops). ArgoCD watches only the GitOps repo. Because the GitOps repo has no triggers back to the App repo, the pipeline terminates cleanly after image deployment.

Q15: How do we achieve zero-downtime rolling updates in Kubernetes?

By defining readinessProbe, livenessProbe, and a rolling update strategy with maxUnavailable: 0 and maxSurge: 1. Kubernetes spins up new Pods, waits until their readiness probe returns HTTP 200, updates the Service Endpoints to include the new Pods, and only then issues a SIGTERM to old Pods.
