01 Dual-Namespace Platform Topology: ml-infra & ml-app

In enterprise distributed systems, monolithic Kubernetes namespaces lead to resource contention, permission bloat, and upgrade lock-in. We structure the cluster into a decoupled Dual-Namespace Architecture separating shared platform infrastructure from containerized workloads:

Why Cross-Namespace Platform Separation Matters

Architecture Pattern Single Monolithic Namespace (Anti-Pattern) ❌ Dual-Namespace Architecture (Enterprise Pattern) 🏆
Lifecycle Decoupling Redis/Kafka redeployed or restarted whenever app code changes. Risk of data drop. Platform runs permanently in ml-infra. App workloads in ml-app deploy 10x/day with zero platform disruption.
Platform Reuse Every new ML service (Fraud, Recommendations) must deploy its own Redis & Kafka instances. Massive RAM wastage. New workloads (e.g. fraud-detection in ml-fraud) simply point DNS to redis-service.ml-infra:6379.
Security & RBAC App developers require broad permissions on the namespace, risking accidental broker deletion. App developers only have access to ml-app. Platform engineers manage ml-infra and secrets.
CoreDNS Resolution Flat naming (redis-service:6379) only works locally. Standardized DNS format: <service-name>.<namespace>.svc.cluster.local (or <service>.<namespace>).

02 Core Application Tier: Dual-Path ML Serving

Why Dual-Path Serving?

Real-world production ML serving requires handling two vastly different traffic profiles:

Serving Path Mechanism Primary Use Case Latency Profile
1. Synchronous Online Path REST API (FastAPI / HTTP) User-facing interactive applications, real-time UI queries Low Latency (< 15ms target)
2. Asynchronous Streaming Path Apache Kafka (Event-Driven) High-volume batch pipelines, IoT ingest, telemetry processing High Throughput (Decoupled, zero backpressure)

A. The Model Layer (model.py)

In this capstone, the inference engine wraps a Scikit-Learn LinearRegression model representing a linear function ($y = 2x$):

def get_model() -> LinearRegression:
    """Returns a singleton trained scikit-learn model."""
    X = np.array([[1], [2], [3], [4]])
    y = np.array([2, 4, 6, 8])
    model = LinearRegression()
    model.fit(X, y)
    return model

B. The HTTP API Layer (main.py)

Built with FastAPI and Pydantic v2 for automatic schema validation and serialization:

  • POST /predict: Accepts a list of floats (input_data: list[float]) and returns predictions.
  • GET /healthz: Liveness probe verifying the Python event loop is unblocked.
  • GET /readyz: Readiness probe verifying that the ML model is initialized in RAM.

C. The Asynchronous Worker Layer (kafka_worker.py)

Uses aiokafka to create an asynchronous loop that reads from the inference-requests topic, executes batch prediction, and pushes results to inference-results with tracking IDs.

03 Caching Strategy & Graceful Degradation

Predictive Caching Mechanics

ML inference is CPU/GPU intensive. If multiple clients query the same input features, recalculating the dot-products is wasted compute. We implemented an MD5 cryptographic cache key design in redis_cache.py:

def cache_key(input_data: list[float]) -> str:
    # 1. Deterministically serialize the floating point input array
    input_str = json.dumps(input_data, sort_keys=True)
    # 2. Hash into fixed-length 32-character hexadecimal digest
    hash_input = hashlib.md5(input_str.encode()).hexdigest()
    # 3. Namespace with model version to prevent stale cache on model retraining
    return f"pred:{MODEL_VERSION}:{hash_input}"

Why Version the Cache Key?

If you retrain your model from v1 to v2, old predictions cached in Redis would return invalid results for identical inputs! By namespacing the key with MODEL_VERSION, updating the version string automatically invalidates all previous cached values without manual cache flushing!

The Graceful Degradation Design Pattern

In distributed systems, external dependencies will fail. Network partitions happen, and Redis pods restart. A junior mistake is allowing Redis connection timeouts to bubble up as HTTP 500 errors to end users.

Our implementation treats the cache as an optimization, not a hard requirement:

async def get_cached_prediction(input_data: list[float]) -> list[float] | None:
    try:
        key = cache_key(input_data)
        cached_value = await redis_client.get(key)
        if cached_value is not None:
            return json.loads(cached_value)
    except Exception as e:
        # LOG AND FALLBACK: The API remains completely functional!
        logger.warning(f"Redis cache lookup failed: {e}. Falling back to model inference.")
    return None

04 Kubernetes Runtime & Hardening

A. Resource Quotas (Requests vs. Limits)

Every pod template in our chart defines strict compute boundaries:

resources:
  requests:
    cpu: 100m      # 0.1 CPU core reserved exclusively for this pod
    memory: 128Mi  # 128 Megabytes guaranteed RAM
  limits:
    cpu: 500m      # Hard throttle ceiling if pod spikes
    memory: 512Mi  # Kernel sends SIGKILL (OOMKilled) if exceeded

B. Pod Security Standards (CIS Benchmark Compliance)

In our Dockerfile and Helm templates, we enforce unprivileged execution:

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 1000
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL

C. Apache Kafka in KRaft Mode (No ZooKeeper)

Historically, Kafka required an auxiliary Apache ZooKeeper cluster. Our setup deploys modern KRaft mode:

  • Consensus handled natively inside Kafka using internal Raft leader voting.
  • Zero external ZooKeeper JVM processes; faster cluster failover (< 3 seconds).

07 Enterprise CI/CD: Quality Gates, OCI Artifacts & Immutable GitOps

In enterprise engineering, pushing unversioned :latest images or untested Helm templates directly to production is an unacceptable risk. Our upgraded CI/CD pipeline enforces strict quality gates, publishes immutable OCI artifacts to GHCR (our cloud Artifactory), and performs automated GitOps writebacks:

Pipeline Job Triggers Tooling Enterprise Verification & Artifact Outcome
1. Quality & Tests Push / PR uv, ruff, mypy, pytest Enforces code formatting, static type checking (0 errors across 5 modules), and passes all 6 unit tests before any container build begins.
2. Helm Chart CI Push / PR helm lint Validates Go template syntax, schema contracts, and value bindings for both helm/ml-infra and helm/ml-app.
3. Immutable Docker Build Push to main Docker Buildx, GHCR Builds hardened container and tags it with deterministic immutable tags: sha-<commit-hash>, v0.1.<build-number>, and latest.

08 Production Observability: Pattern A (Fluent Bit DaemonSet)

A. The Architectural Decision: Pattern A vs. Pattern B

In Kubernetes, there are two primary approaches to shipping logs to Splunk. In enterprise production, Pattern A is strictly preferred:

Evaluation Criteria Pattern A (DaemonSet Forwarder - Fluent Bit) 🏆 Pattern B (Direct App Telemetry) ❌
12-Factor Compliance Factor XI Compliant: App only writes structured JSON to stdout. Zero knowledge of Splunk or tokens. Coupled: App code imports HTTP clients, manages Splunk tokens, and handles retries.
Crash & OOM Survivability Survives Crashes: If Python crashes, segfaults, or is OOMKilled, logs on disk are still shipped to Splunk. Silent Drop: If process terminates abruptly, pending in-memory telemetry is permanently lost.
Multi-Service Coverage Cluster-Wide: Automatically collects logs from Redis, Kafka, and ML API with zero application code. Siloed: Only captures code manually instrumented. Redis and Kafka remain completely dark.
Latency Impact Zero: Writing to stdout buffer is sub-microsecond. Fluent Bit handles batching, disk buffering, and retries. Overhead: Background HTTP tasks compete for Python event loop cycles during network degradation.

B. How the Log Transport Pipeline Works

+----------------------+ +----------------------+ +----------------------+ | ML API Replicas x2 | | Redis Cache Pod | | Kafka Broker Pod | | (stdout JSON stream) | | (stdout server logs) | | (stdout cluster logs)| +----------------------+ +----------------------+ +----------------------+ | | | +-----------------------------+-----------------------------+ | v +--------------------------------------+ | Kubelet writes to Node HostPath | | /var/log/pods/<namespace>_<pod>/* | +--------------------------------------+ | v (inotify tail) +--------------------------------------+ | Fluent Bit (DaemonSet: 1 per node) | | - INPUT: tail /var/log/pods/ | | - FILTER: kubernetes metadata enrich | | - OUTPUT: HTTP HEC (/raw endpoint) | +--------------------------------------+ | | HTTPS POST (Batch JSON) v +--------------------------------------+ | Splunk Enterprise (HEC Port: 8088) | | Token: 2a58141a-232e-41ea-... | +--------------------------------------+

09 Declarative Kafka Platform & Kafka UI Dashboard

A. The Problem with Imperative CLI Topic Creation

In immature setups, engineers run manual kafka-topics.sh --create commands after deployment. This causes severe production failure modes:

  • Race Conditions: Producers start before topics exist, triggering UNKNOWN_TOPIC_OR_PARTITION errors.
  • Configuration Drift: Partition counts and retention policies in dev never match staging or production.
  • Non-Reproducible Clusters: If the cluster is recreated from scratch, topics are missing.

B. The Kubernetes Job Pattern with Init Containers

We deploy an automated Kubernetes Job (helm/ml-infra/templates/kafka-topics-job.yaml) that runs idempotently during deployment:

  1. Init Container (Wait for Broker): Polls kafka-service:9092 with kafka-broker-api-versions.sh until Kafka completes internal KRaft election.
  2. Main Container (Topic Provisioner): Runs kafka-topics.sh --create --if-not-exists --topic <name> --partitions 3 for inference-requests and inference-results.

C. Kafka UI Dashboard (NodePort 30880)

We deploy Provectus Kafka UI (provectuslabs/kafka-ui) in ml-infra exposed on NodePort 30880 (http://localhost:30880). It provides an instant web UI to inspect topic partitions, consumer group lag, and message contents without SSH access.

A. Secrets vs. ConfigMaps

Sensitive credentials (Splunk HEC tokens, Redis passwords, Kafka SASL credentials) must never be stored in plain ConfigMaps or committed to Git. We package an opaque Kubernetes Secret:

B. The Cloud-Native Pattern: External Secrets Operator (ESO)

In production enterprise GitOps, committing Secrets even in base64 to Git is forbidden. The industry standard is External Secrets Operator (ESO):

+----------------------------+ | Cloud Secret Store | | (AWS Secrets Mgr / Vault) | +----------------------------+ | v (Authenticated Sync) +----------------------------+ | External Secrets Operator | <-- Reads 'ExternalSecret' CRD from Git | (Controller in k8s) | +----------------------------+ | v (Generates inside cluster) +----------------------------+ | Native Kubernetes Secret | <-- Injected into Pods via envFrom/secretKeyRef | (Never committed to Git) | +----------------------------+

Developers commit an ExternalSecret manifest to Git referencing the Vault secret path. ESO pulls the token at runtime and mounts it into the application pod.

11 Real War Stories: Bugs Hit & How We Fixed Them

These are real bugs encountered during this build—the kind of edge cases you only learn from hands-on production engineering:

Bug 1: The `async def` without `await` Trap

Symptom: High concurrency latency spikes even though the handler was declared async def.

Root Cause: Declaring a function async def does not make code non-blocking! Using a synchronous client (e.g. standard redis.Redis) without await blocks Python's entire single-threaded event loop for every concurrent user request.

The Fix: Use redis.asyncio and ensure every I/O call is explicitly awaited: await redis_client.get(key).

Bug 2: Calling `async` Function Without `await` Silently No-ops

Symptom: Cache writes never appeared in Redis, but no exception was thrown.

Root Cause: In Python, calling an async def function without await does not execute the function body; it returns an unexecuted coroutine object. Python emits a warning, but execution continues.

The Fix: Always write await cache_prediction(...) at the call site.

Bug 3: Docker Layer Cache Broken by `uv-build`

Symptom: RUN uv sync --frozen --no-dev --no-install-project failed with cause: failed to open file /app/README.md.

Root Cause: pyproject.toml specified readme = "README.md". When building the package, the build backend validated the presence of the readme file, which was missing from the layer.

The Fix: Copy README.md alongside pyproject.toml and uv.lock before running uv sync.

Bug 4: Kubernetes CRD Annotation 256KB Exceeded

Symptom: kubectl apply -f install.yaml for ArgoCD failed with metadata.annotations: Too long: must have at most 262144 bytes.

Root Cause: Client-side kubectl apply stores the entire previous manifest inside kubectl.kubernetes.io/last-applied-configuration, exceeding the 256KB annotation limit for massive CRDs.

The Fix: Use Kubernetes Server-Side Apply: microk8s kubectl apply --server-side -f install.yaml.

Bug 5: ArgoCD "Remote Repository is Empty" Error

Symptom: ArgoCD application reported ComparisonError: failed to list refs: remote repository is empty.

Root Cause: The ArgoCD Application was applied before local Git commits were pushed to the remote GitHub repository.

The Fix: Push commits to GitHub first (git push -u origin main), then trigger hard refresh.

Bug 6: Fluent Bit SQLite on Read-Only Volume Crash

Symptom: Fluent Bit pod entered CrashLoopBackOff with [error] [sqldb] cannot open database /var/log/flb_kube.db.

Root Cause: /var/log was mounted into the pod as readOnly: true for security. Fluent Bit tried to write its state tracking database to that read-only path.

The Fix: Point the database to container-writable memory/tmpfs: DB /tmp/flb_kube.db.

Bug 7: The Infinite Log Storm Feedback Loop

Symptom: Fluent Bit log volume spiked exponentially to thousands of log events per second.

Root Cause: Fluent Bit logged a warning to stderr. Because Fluent Bit was deployed in the same cluster, its own log was written to /var/log/pods/, which Fluent Bit read and shipped to Splunk, triggering another log line in an infinite loop.

The Fix: Add an exclusion pattern to the tail input: Exclude_Path /var/log/pods/*_fluent-bit*/*/*.log.

Bug 8: Splunk HEC Plugin Parameter Compatibility

Symptom: Fluent Bit emitted warnings [warn] [record accessor] translation failed, root key=hec_token.

Root Cause: The generic splunk output plugin in Fluent Bit v3 expected token keys embedded in individual log records when not explicitly formatted.

The Fix: Switch to the universal http output plugin targeting URI /services/collector/raw with header Authorization Splunk <token>.

Bug 9: Grafana JSON Template Curly Braces Escaping in Helm

Symptom: helm lint failed with function "status" not defined.

Root Cause: Grafana dashboard JSON contains legend format strings like HTTP {{status}} and {{kubernetes_pod_name}}. The Go template engine in Helm attempted to evaluate these as Helm template functions.

The Fix: Escape double curly braces in Helm templates using string literals: "legendFormat": "HTTP {{ `{{status}}` }}".

Bug 10: ArgoCD Shared Resource Conflict on ClusterRoleBinding

Symptom: ArgoCD flagged SharedResourceWarning: ClusterRoleBinding/fluent-bit-read is part of applications argocd/ml-infra and ml-serving-capstone.

Root Cause: Cluster-scoped resources (ClusterRoles, ClusterRoleBindings) cannot be managed by two distinct ArgoCD applications with pruning enabled simultaneously.

The Fix: Delete obsolete monolithic application from ArgoCD before rolling out the decoupled infrastructure application.

13 Senior Engineering Revision Q&A

Q1: Why is GitOps (Pull model) considered strictly superior to traditional CI/CD (Push model)?

Answer: In the traditional push model, your CI server possesses permanent administrative cluster credentials. If CI is breached, attackers gain full cluster root access. In the GitOps pull model, the cluster never accepts inbound connections; ArgoCD runs inside the cluster behind firewalls and pulls manifests unidirectionally from Git.

Q2: What is the exact difference between a Liveness Probe and a Readiness Probe?

Answer: A Liveness Probe detects whether the process is deadlocked or frozen; if it fails, Kubernetes terminates and restarts the container. A Readiness Probe detects whether the container is ready to accept user requests (e.g. model loaded in RAM); if it fails, Kubernetes does NOT kill the pod, but temporarily removes it from Service endpoints.

Q3: How does Cross-Namespace DNS resolution work in Kubernetes?

Answer: Standard intra-namespace DNS only requires the service name (e.g. redis-service), which CoreDNS appends with the pod's namespace. For cross-namespace communication, the fully qualified domain name (FQDN) or namespace-qualified name is required: redis-service.ml-infra.svc.cluster.local or simply redis-service.ml-infra.

Q4: How does Prometheus discover pods without maintaining a static list of IP addresses?

Answer: Prometheus uses the Kubernetes API Service Discovery (`kubernetes_sd_configs: [role: pod]`). Through a ClusterRole with read access to pods, Prometheus watches the API server and evaluates Pod Annotations. If prometheus.io/scrape: "true" is present, Prometheus dynamically registers the Pod IP and port into its active scrape pool.

Q5: Why did we use an Init Container in the Kafka Topic Creation Job?

Answer: When Kubernetes launches a Job concurrently with a StatefulSet/Deployment, the broker pod may be scheduled but still initializing its KRaft metadata log. An Init Container polls the broker port with kafka-broker-api-versions.sh until the cluster reports ready, preventing premature job crashes.
